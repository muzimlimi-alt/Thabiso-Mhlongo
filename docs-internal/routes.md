# server.js Route Inventory

Generated by exhaustive read-through of `server.js` (19,260 lines) on 2026-08-27, as Phase 1
(read-only reconnaissance) of a housekeeping effort. No files other than this one were modified.

**Route count: 329 total (270 `/api/admin`, 49 `/api/public`, 10 Other).** This matches the
~329 baseline exactly (270/49/10), so the baseline is current — no missed routes, no drift.

## Method notes

- Every route in this file is registered via a plain `app.get/post/put/patch/delete(path, ...mw, handler)`
  call. There are **no** `app.route(...).verb().verb()` chains and **no** separate `express.Router()`
  instances mounted with `app.use(prefix, router)` anywhere in the file — confirmed by grepping for
  `.route(`, `Router(`, and `app.use(` (only bare middleware/static/session/error-handler registrations
  found, listed below). So the full route surface is exactly the 329 direct verb calls found by
  `grep -n "app\.\(get\|post\|put\|patch\|delete\|all\)("`.
- No `app.all(` usage, no dynamically-built path strings, no routes registered in a loop.
- One route (`POST /api/public/bookings/:id/attachments`, line 14368) spans multiple source lines —
  the path is on the `app.post(` line but the multer middleware and handler are on following lines;
  it is still a single, ordinary registration.
- Global middleware registered near the top of the file (lines 295–504) applies to **every** request
  regardless of path, in this order: `helmet()` (CSP/security headers) → HTTPS redirect in production →
  `cors()` → `express.json({limit:'50kb'})` / `urlencoded` → a custom XSS body-escaper → a custom
  NoSQL-injection sanitizer → a request logger → a path-blocklist guard (blocks `/.git/`, `/backups/`,
  `.env`, `.sqlite`, etc.) → `express.static('/')` (serves the whole repo root as static files, so any
  file not caught by the blocklist above is directly downloadable) → `express-session` (SQLite-backed,
  `httpOnly`, `secure` in production). **There is no blanket `app.use('/api/admin', ...)` auth
  middleware** — every admin route individually includes `requireAdmin` (or, in 2 cases noted below,
  an inline equivalent/absent check). A 404 handler and a generic error handler are registered last
  (lines 18531, 18536).
- Auth/RBAC middleware, defined once near line 1898–1956 and referenced per-route below:
  - **`requireAdmin`** (array: `[adminRateLimiter, sessionCheckFn]`) — requires `req.session.adminId`
    to be set (i.e. a valid admin login session); also enforces `must_change_password` lockout (only
    `/force-change-password`, `/logout`, `/session` remain reachable) and re-checks the admin's
    `is_active` flag on every request, destroying the session if suspended. No role restriction by
    itself — any authenticated admin (`administrator`, `manager`, or `assistant`) passes.
  - **`requireRole([...roles])`** — layered *after* `requireAdmin` on routes that need more than "any
    logged-in admin"; reads `req.session.role` (defaults to `'assistant'` if unset) and 403s if not in
    the allowed list. Three roles exist: `administrator`, `manager`, `assistant`.
  - **`requireRoleForInquiryEmail`** — custom, used only on the 4 `direct-emails` mutation routes;
    lets `assistant` compose/send freeform email but blocks them from replying on an inquiry-linked
    thread (administrator/manager only for those).
  - **`requireBookingAccessToken`** — used on public "tracking" routes; requires a bearer
    `access_token` (JSON body or query string) issued by the `/track/verify-code` OTP flow, matched
    against a hashed, expiring `booking_access_tokens` row scoped to that specific booking id. This is
    the public equivalent of admin auth — not a login, but proof the caller controls the booking's
    email inbox.
  - Various **rate limiters** (`ipRateLimiter`, `bookingRateLimiter`, `mutateRateLimiter`,
    `otpRequestRateLimiter`, `trackRateLimiter`, `lookupRateLimiter`, `exportRateLimiter`,
    `adminRateLimiter` (baked into `requireAdmin`), `adminLoginRateLimiter`, `payfastItnRateLimiter`,
    `sitemapRateLimiter`, `analyticsTrackLimiter`) are layered on many routes — these throttle, they do
    **not** authenticate, so they are not listed as "Auth" in the tables below.
- Per-route tables below list only *additional* role requirements beyond the blanket rule for that
  group (i.e. beyond "any logged-in admin" for `/api/admin`, and "none" for `/api/public`).

## Notes

**Final count:** 329 routes — 270 `/api/admin`, 49 `/api/public`, 10 Other. This matches the ~329
baseline exactly (270/49/10 predicted vs. 270/49/10 found), so the prior measurement is confirmed
current, not stale. Verified two independent ways: (1) manual enumeration while reading the file
top-to-bottom, (2) a small Node script executed via Bash that regexed every
`app.<verb>('<path>', ...)` call and bucketed by path prefix — both gave 329/270/49/10.

**Deviations from a plain `app.verb(path, handler)` shape found while reading:**
- `POST /api/public/bookings/:id/attachments` (line 14368) spreads its middleware/handler across
  multiple lines (`app.post(path,\n  rateLimiter, ipLimiter,\n  upload.array(...),\n  (req,res)=>{...})`)
  — still one ordinary registration, just multi-line for readability.
- `POST /upload` (line 661) and `POST /api/bookings/:id/payment-logs` (line 6034) do **not** use the
  `requireAdmin` middleware array at all — they inline their own (much weaker/differently-shaped)
  session checks. `/upload`'s inline check (`req.session.adminId`) is functionally equivalent to
  `requireAdmin`'s core check, done that way only because the route is registered ~1,200 lines before
  `requireAdmin` is defined (a comment in the source confirms this is deliberate: "this route is
  defined above the `requireAdmin` const... so it can't use that middleware"). `/api/bookings/:id/payment-logs`'s
  inline check (`req.session.admin`) appears to be a leftover/typo referencing a session field that is
  never set anywhere else in the file — this route is very likely unreachable/dead code today rather
  than intentionally admin-gated the way `/upload` is; worth a follow-up ticket rather than a Phase-1 fix.
- No `app.route(...).get().post()` chains, no `express.Router()` sub-routers mounted via `app.use`, no
  path built by string concatenation, and no route registered inside a loop — the entire file is 329
  independent, statically-written `app.<verb>(literal-path, ...)` calls plus 13 non-route
  `app.use(...)` calls (helmet, https-redirect, cors, json/urlencoded body parsers, XSS sanitizer,
  NoSQL sanitizer, request logger, path blocklist, `express.static`, `express-session`, and the
  final 404 + error handlers).
- There is **no** blanket `app.use('/api/admin', requireAdmin)` — every one of the 270 admin routes
  (except the 2 noted above) individually lists `requireAdmin` as explicit middleware. This is worth
  knowing for the housekeeping effort: a future refactor to a router-based structure with prefix-level
  auth would be a behavior-preserving simplification, not a new restriction, *except* it would also
  silently fix `/api/bookings/:id/payment-logs`'s broken inline check and would need `/upload`'s
  early-definition constraint resolved (e.g. by moving `requireAdmin`'s definition earlier in the file).
