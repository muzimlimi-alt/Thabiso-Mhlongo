# Email System Audit — Verified Inventory (Prompt 1)

> **Read-only audit.** No code, templates, or emails were changed. Line references are to
> `server.js` unless stated. Generated by tracing every `sendEmail(` call site and each
> `send*Email` function's trigger (call site) and recipient.

## 1. How the email system actually works (architecture)

The pack (Prompt 2) assumes per-template HTML. Reality is a **centralised queue + wrapper**:

1. **`sendEmail({ to, subject, htmlContent, attachments, titleOverride, skipBrandAttachments,
   trigger_event, … })`** (`js/emailService.js:92`) does **not** send — it **queues** a row into
   the `notifications` table (`type='email'`, `status='pending'`). The per-email code only ever
   supplies the **body** HTML (`htmlContent`) + subject + recipient.
2. A queue processor later calls **`sendEmailDirectly()`** (`js/emailService.js:147`), which:
   - **Feature-flagged by `EMAIL_OVERHAUL_ENABLED`.**
     - **OFF (legacy):** sends `htmlContent` **as-is** — the bespoke body HTML, no wrapper, no
       central banner. **There is no `.env` in the repo, so the flag is currently unset → the
       legacy path is what ships today.**
     - **ON (branded):** wraps the body with **`createEmailWrapper(body, title, unsubscribeUrl,
       bannerSrc, socialLinks)`** (`js/emailTemplates.js:12`), attaches the **single global banner**
       (`cid:thabisoBanner` from `emailAssets.getBrandAttachments()`, else `EMAIL_BANNER`), looks up
       an unsubscribe token (only if the recipient is a newsletter subscriber) and active social links.
3. **Shared components today:** `createEmailWrapper` (600px dark "Editorial-Luxe" shell + banner slot
   + footer/unsubscribe/social) and `createQuoteTable(rows)` (`js/emailTemplates.js:164`). Nothing
   else — no `cta_button`, `info_card`, `alert_strip`, `system_header`, etc.

**Implications for the redesign:**
- **Banner is global, not per-email.** Every email that goes through the branded path gets the *same*
  banner. The "banner_id per template" model (Prompt 5) does not exist yet — `banner_id` column,
  registry, and per-category art are all net-new.
- **`createEmailWrapper` is the only "base_layout"/"header"/"footer"/"banner_slot" today** and it's
  bypassed entirely on the legacy path. Prompt 2's components should extend this file, and the flag
  behaviour must be reconciled (right now branding is effectively off).
- **`js/notificationService.js` is client-side toasts/modals — NOT email.** Excluded from this audit.

## 6. Branding inconsistencies, duplicate markup & technical debt

1. **Branding is effectively OFF in this checkout.** `EMAIL_OVERHAUL_ENABLED` is unset (no `.env`),
   so `sendEmailDirectly` takes the **legacy branch** and emails ship each function's **raw body HTML
   with no wrapper, banner, footer, or unsubscribe**. The redesign must decide whether to remove the
   flag or default it on.
2. **No component system beyond two helpers.** Only `createEmailWrapper` + `createQuoteTable` exist.
   Every button, card, and alert is hand-rolled inline in ~56 places → Prompt 2's `cta_button`,
   `info_card`, `alert_strip`, `system_header`, `divider/spacer`, `footer` are all net-new.
3. **Global single banner, no per-email art.** All branded emails share one banner (`cid:thabisoBanner`
   / `EMAIL_BANNER`). No `banner_id`, no category mapping — Prompt 5's registry is greenfield.
4. **Inconsistent, hard-coded styling in bespoke bodies.** e.g. Test Notification uses
   `font-family:Arial` on `#0a0a0a` (not the Outfit/Cormorant stacks, not the Editorial-Luxe tokens);
   gold is hard-coded as `#D4AF37` inline throughout rather than a shared token. Many bodies assume
   the wrapper will supply the shell, so standalone they fail the pack's dark-mode HARD RULES
   (no `bgcolor` redundancy, no `color-scheme` meta, web-font reliance).
5. **Duplicate markup.** Contract-sign reminder is emitted from two call paths (`6611`/`6657`) with
   near-identical bodies; payment/deposit/confirmed emails repeat the same detail-block scaffolding.
6. **System emails mix into the premium wrapper.** Admin/ops alerts currently pass through the same
   `createEmailWrapper` (photographic banner + social footer) rather than a compact `system_header` —
   Prompt 4's split is justified. `skipBrandAttachments:true` is used inconsistently (only a few).
7. **Dual-send functions** (`sendBookingReceivedEmail`) emit both a PREMIUM and a SYSTEM email — keep
   this in mind when rebuilding so the two halves land in the correct track.
8. **Plain-text alternatives** are auto-derived (`htmlToPlainText`) only on the branded path; the
   legacy path sends **no `text/plain` part** → deliverability gap (Prompt 8 item).
